= Problèmes connus
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ./media/


[role="lead"]
Les problèmes connus identifient les problèmes susceptibles de vous empêcher d'utiliser cette version du produit avec succès.

Les problèmes connus suivants ont une incidence sur la version actuelle :



[[trident-node-pods-might-detach-in-use-volumes-during-upgrade-to-26-10-0]]
== Les pods de nœud Trident peuvent détacher les volumes en cours d'utilisation lors de la mise à niveau vers 26.10.0.

Ne mettez pas à niveau vers Trident 26.10.0 depuis Trident 25.10 ou toute version antérieure. Au démarrage, les pods de nœud Trident peuvent détacher des volumes encore en cours d’utilisation. Les pods concernés peuvent échouer avec l’erreur `volume ... is not staged`. Un correctif est en cours de développement. Attendez qu’une version incluant ce correctif soit disponible avant d’effectuer la mise à niveau.



[[volumes-remain-attached-after-upgrading-from-trident-22-10-or-earlier]]
== Les volumes restent attachés après la mise à niveau depuis Trident 22.10 ou une version antérieure

Ce problème concerne les clients qui effectuent une mise à niveau directe de Trident 22.10 ou d'une version antérieure vers Trident 26.10 alors que des volumes sont attachés. Les mises à niveau depuis Trident 23.01 ou une version ultérieure ne sont pas concernées.

Après la mise à niveau, il est possible que les volumes concernés ne se détachent pas. Les pods utilisant des volumes ReadWriteOnce (RWO) ne peuvent pas être déplacés vers un autre nœud et peuvent signaler une erreur de multi-attachement. La suppression du PersistentVolume (PV) peut également se bloquer.

Pour contourner ce problème, sur le nœud qui possède l’attachement de volume obsolète, supprimez le fichier restant `volumePublishInfo.json` du répertoire `globalmount` de ce volume.



[[volumesnapshots-not-reaching-readytouse-state]]
== VolumeSnapshots n'atteignent pas l'état ReadyToUse

[WARNING]
====
Il existe un problème connu avec le `csi-snapshotter` sidecar. Dans toutes les versions de Kubernetes, VolumeGroupSnapshots `v1beta1` empêche VolumeSnapshots d'atteindre l' `ReadyToUse` état.

====
Deux solutions de contournement sont disponibles :

. Supprimez les CRD VolumeGroupSnapshots pour désactiver VolumeGroupSnapshots, puis réinstallez Trident.
. Installez VolumeGroupSnapshots `v1beta2` et `snapshot-controller` la version 8.4.0 ou ultérieure, puis réinstallez Trident. VolumeGroupSnapshots ne fonctionnent pas sur les versions de Kubernetes antérieures à la v1.34.




[[restoring-restic-backups-of-large-files-can-fail]]
== La restauration des sauvegardes Restic de fichiers volumineux peut échouer

Lors de la restauration de fichiers de 30 Go ou plus à partir d'une sauvegarde Amazon S3 effectuée à l'aide de Restic, l'opération de restauration peut échouer. En guise de solution de contournement, sauvegardez les données en utilisant Kopia comme outil de transfert de données (Kopia est l'outil de transfert de données par défaut pour les sauvegardes). Se référer à https://docs.netapp.com/us-en/trident/trident-protect/trident-protect-protect-apps.html["Protégez les applications à l'aide de Trident Protect"^] pour les instructions.
